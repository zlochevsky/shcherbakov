# План: фотографии концертов (и не только)

Записано 2026-11-08 по обсуждению с владельцем.

**Сделано 2026-11-09:** снимки со старой страницы перенесены (290 из 291, `scripts/legacy-photos-sync.py`), в каталоге
концертов — обложка в раскрытом концерте и фильтр «Фотографии»; шаблон читает снимки прямо из `static/photos`
(`images.Config`, `resources.FromString`), без `module.mounts`: `config/_default/module.json` в git не входит, и
подключение в нём до сборки в GitHub Actions не дошло бы. Кэш обработанных картинок Hugo (`resources/`) — в
`.gitignore`. **Не сделано:** просмотр поверх страницы (пока ни один снимок не шире 500 точек — ссылка ведёт
просто на файл), поля `photos_*` в Directus, галерея концерта; 1 снимок ждёт своего события в базе (ниже).

**Первая цель** — снимок у концерта в каталоге концертов, как на старой странице
(`lambda.mkshch.com/fans/utf/concerts.html`, фильтр «Фотографии / Без фото»). Схема рассчитана и на большее:
несколько снимков у концерта, полноразмерные снимки, добавленные позже, снимки из галерей «Картинок»,
фото не только с концертов.

## Как сейчас на старой странице

- Снимки у 290 концертов из 724, по одному, всего 291 файл (1982–2026), все 324×432, вертикальные.
- Сохранены с качеством JPEG 99 — ≈120 КБ каждый, ≈35 МБ все; без `loading="lazy"` браузер, по всей видимости,
  грузит их все сразу, хотя концерты свёрнуты.
- Имена — по дате: `conphoto/ГГГГММДД.jpg`, у двух концертов одного дня `_1`/`_2` (дневной и вечерний).
- Ни автора, ни подписей, ни `alt` нет. «Увеличение» по нажатию — CSS `.image:active { transform: scale(1.2) }`,
  пока нажата кнопка мыши; **не переносим** (решение владельца): большой версии нет, а курсор-лупа обещает её.

## Где лежат снимки

- **Снимки события** — файлами в репозитории, в `static/photos/<id события>/` (вне `Images/`: это витрина,
  а не фан-клуб). Имя каталога — `events.id` (`L2024-04-21-1`); слова «concert» в имени нет: фото бывают
  не только с концертов. Снимков сколько угодно, порядок — по имени файла (`01.jpg`, `02.jpg`…).
- Шаблон находит каталог по `id` сам (`os.FileExists`, `os.ReadDir`): нет каталога — нет и снимка; поле
  в Directus для этого не нужно.
- **Снимки из других мест** (старые фото концертов в галереях `Images/photos*`, файлы в `Images/concert/`)
  к событию привязываются полем в Directus (ниже) — без переноса и копий.

**Граница витрины и клуба.** Встроенная картинка из `Images/` её не нарушает: `check-separation.py` проверяет только
ссылки (`<a href>`). Ссылка из каталога концертов на страницу галереи — переход витрина → клуб, только исключением
в `ALLOW` (как у «Новостей» на афиши и баннеры). Открытый вопрос: не признать ли «Фотографии» с концертов витриной,
как «Архив» концертов (снимок концерта — документ о концерте, а не творчество поклонников), — это пересмотр решения
2026-09-23 «Картинки — клуб целиком»; решает владелец.

## Поля события в Directus

Подписи почти всегда относятся к концерту целиком, а не к снимку: в галереях «Фотографии» (8 страниц, 99 разделов,
427 снимков) строка об авторе — одна на раздел (86 из 99: «С концерта 28.10.2017 в Оренбурге. Автор — …,
оригинал в ВК»), подписи под отдельными снимками — у ≈50, и те о месте («Питер», «Хайфа»). Поэтому отдельной таблицы
снимков нет, только поля у `events`:

| Поле | Что |
|---|---|
| `photos_author` | автор снимков (несколько — через запятую) |
| `photos_source` | ссылка на оригинал (ВК, Facebook…), необязательно |
| `photos_extra` | пути от корня сайта к снимкам из других мест (`Images/concert/Ornb_6856.jpg`, …), по одному в строке |

У большинства концертов все три пусты: снимки находятся в `photos/<id>/` сами, авторы старых 291 неизвестны.
Своя подпись у отдельного снимка — когда понадобится: в имени файла (`03-Хайфа.jpg`) или небольшим файлом в каталоге
снимков. При сборке шаблон проверяет, что пути из `photos_extra` существуют, и предупреждает, если нет.

## Порядок и обложка

- Общий порядок: файлы `photos/<id>/` по имени, затем `photos_extra` в порядке строк.
- **Обложка** (снимок в каталоге) — первый снимок: в своём каталоге её задаёт имя `01.jpg`, без своего каталога —
  первая строка `photos_extra`. Отдельного поля «обложка» нет: порядок уже задан именами и списком.

## Превью и просмотр

- **Превью делает Hugo** при сборке, встроенной обработкой картинок (библиотека на Go; ImageMagick сборке не нужен):
  шаблон читает файл из `static/photos` (`os.ReadFile` → `resources.FromString`), затем `images.AutoOrient`
  (поворот по EXIF), потом `.Fill "324x432 Smart"`: все превью одной рамки, как сейчас, Hugo оставляет самую
  насыщенную деталями часть кадра; у горизонтальных снимков (в галереях их большинство, 800×533) края обрезаются,
  полный кадр — при открытии. Снимок, который уже не больше рамки (старые 324×432), выводится как есть.
- **Ссылка** на снимок — только если он заметно больше превью (шире 500 точек): тогда щелчок открывает снимок
  **поверх страницы**; остальные снимки концерта листаются стрелками (на телефоне — свайпом), под снимком — автор
  и ссылка на оригинал, Escape или щелчок мимо закрывают. Свой небольшой скрипт и стили, без сторонних библиотек.
  Маленький одиночный снимок не кликабелен.
- Несколько снимков — пометка в углу обложки («1/6» или «+5»).
- Все снимки — с `loading="lazy"`: при раскрытии концерта грузится одна обложка, остальные — при листании.
  Фильтр «Фотографии / Без фото» — по наличию снимка.
- **Полноразмерный снимок позже** встраивается без правки кода: в `photos/<id>/` кладётся большой файл вместо
  маленького (тем же именем) — при сборке у него появятся превью и ссылка. Поэтому сразу: старые снимки — в схему
  `photos/<id>/01.jpg`, шаблон — с правилом «ссылка только у большого».
- **Галерея концерта** (все снимки) — не решено: в раскрытом концерте каталога (тот же просмотр поверх страницы)
  или на отдельной странице концерта (генератор страниц по Directus — отдельная задача).

## Размер и скорость (замеры 2026-11-08)

- Перед коммитом большие снимки уменьшаются до 2000 точек по длинной стороне:
  `magick mogrify -resize '2000x2000>' -quality 85 *.jpg` (снимок с телефона — 2,7 МБ → 380 КБ, поворот по EXIF
  сохраняется). В git каждый файл остаётся навсегда.
- Старые 291 — один раз пережать с качеством 82: ≈35 КБ вместо ≈120, все ≈10 МБ вместо ≈35. Владелец сравнил
  оригинал, magick 82 и Hugo (Go) 82 — разницы не видно (Go хранит цвет в половинном разрешении, 4:2:0, и чуть
  меньше по размеру).
- Первая обработка в Hugo — ≈0,35 с на снимок с 2000 точек (только превью), повторная сборка берёт готовые превью
  из `resources/_gen` за доли секунды. В GitHub Actions этот кэш между запусками теряется — при сотнях снимков
  сохранять его (`actions/cache`), иначе каждая сборка обрабатывает всё заново.
- По превью на концерт за последние 10 лет — ≈170 снимков (опубликованных концертов в 2016–2026 — 168).

## Перенос старых снимков

- Имена переводятся в id событий автоматически: `ГГГГММДД.jpg` → `L<ГГГГ-ММ-ДД>`, `_1`/`_2` → `-1`/`-2`.
  На 2026-11-08 совпали 258 из 291; остальные 33 — вручную: концерты 2024–2026, которых в базе ещё нет (за 2026
  на старой странице снимков ≈20, в базе опубликовано 7 концертов — база отстаёт), несколько неточных дат
  (`19890000`) и дат, записанных в базе иначе.
- Порядок: внести недостающие концерты в базу → скрипт переноса (скачать, пережать, разложить в `photos/<id>/01.jpg`,
  список несовпавших) → шаблон каталога → фильтр.
- **Итог 2026-11-09.** Концерты 2024–2026 внесены `scripts/legacy-concerts-sync.py`; `scripts/legacy-photos-sync.py`
  перенёс 290 снимков из 291 (≈34 МБ → ≈14 МБ; у новых снимков ≈50 КБ, а не 35). Его можно запускать снова: снимок
  берётся, только если папки события ещё нет, — новые снимки со старой страницы докачиваются, перенесённые и
  заменённые не трогаются. Ручные сопоставления — в `scripts/legacy-photos-sync.json` (`19960400.jpg` →
  `L1996-04-xx`). Три снимка дождались своих концертов после синхронизации старых лет (`19880615`, `19980218`,
  `20030601`); ждёт события в базе только `19890000` (ДК МЭЛЗ, дата неточная — событие заводится вручную, затем
  строка в JSON).

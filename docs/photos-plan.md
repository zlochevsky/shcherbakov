# План: фотографии концертов (и не только)

Записано 2026-11-08 по обсуждению с владельцем. Что уже работает (снимки в `static/photos/<id события>/`, обложка
и фильтр «Фотографии» в каталоге концертов, превью Hugo, перенос со старой страницы), описано в README («Фотографии»);
здесь — только то, что осталось.

## Граница витрины и клуба

**Правило (владелец, 2026-11-11):** граница — по снимку, а не по галерее. Снимок, привязанный к концерту, — витрина:
свой файл в `static/photos/<id>/` или снимок из галерей «Картинок» (`Images/photos*`, `Images/concert/`), показанный
у концерта без переноса и копий. Галереи остаются клубом целиком: там и снимки из кулуаров, и со слётов — их к концертам
не привязывают (или привязывают к событию, если они с него). Кулуарный снимок на витрине — отдельное решение о нём,
не о разделе. См. `docs/site-structure-analysis.md`, §4.

Встроенная картинка из `Images/` границу не нарушает: `check-separation.py` проверяет только ссылки (`<a href>`).
Ссылка из каталога концертов на страницу галереи — переход витрина → клуб, только исключением в `ALLOW` (как у
«Новостей» на афиши и баннеры).

## Снимки — в файловом хранилище Directus

**Решено владельцем 2026-11-12** (после пробы на 16 сканах концерта `L1993-06-11`, ≈93 МБ): снимки не в git. В git
должен попадать уже уменьшенный файл, значит, уменьшать вручную перед каждой загрузкой — неустранимый шаг. Обычная
схема: редактор загружает оригинал в форме события, нужные размеры Directus делает сам (`/assets/<id>?key=<пресет>`),
Hugo при сборке забирает готовые копии; сайт остаётся статическим. Мастер-сканы хранит владелец у себя; на сервер —
оригинал или копия до ≈3000 точек, по выбору.

### Правила загрузки снимков (владелец, 2026-11-12)

Directus — не архив: в него загружают копию для публикации, а не оригинал.

1. **Оригиналы в Directus не загружают.** Мастер-сканы и полноразмерные файлы с фотоаппарата хранятся у владельца
   в личном архиве (с резервными копиями). Снимок, присланный со стороны, сначала сохраняют там же как есть.
2. **Предел — 3000 точек по длинной стороне**, JPEG с качеством около 90; файл обычно 1–2 МБ, не больше 3 МБ.
   Снимок меньше предела загружают без изменений, не увеличивают и не пережимают.
3. **Ориентацию и кадр правят до загрузки**, в оригинале: зеркальный скан отражают, лишние поля обрезают. Редактор
   Directus (отразить, повернуть, обрезать) — для разовых поправок уже загруженного снимка.
4. **Сведения о файле** (EXIF сканера, данные фотоаппарата) можно не сохранять; GPS-координаты из снимков с телефона
   убирают.
5. Один снимок — один файл: без коллажей, рамок и подписей поверх изображения; подпись, автор и источник — в полях
   файла.

Как уменьшить (ImageMagick; оригинал не трогается, копия пишется в папку `web/`):

```
mkdir -p web && for f in *.jpg; do magick "$f" -resize '3000x3000>' -quality 90 -strip "web/$f"; done
```

`3000x3000>` уменьшает только то, что больше предела. Без командной строки — любым редактором с экспортом
(«Сохранить для веб», «Изменить размер»): длинная сторона 3000, качество 90.

Не решено:

- **Проверка предела в Directus:** штатно Directus разрешение при загрузке не проверяет; можно ограничить хотя бы
  размер файла (`FILES_MAX_UPLOAD_SIZE` в `.env`, например `5mb`) — тогда полноразмерный скан не пройдёт.
- **Где лежат файлы хранилища:** диск сервера Directus (по умолчанию) или S3-совместимое облако (штатный драйвер
  Directus `s3`: Cloudflare R2, Backblaze B2 и т. п.); проверить свободное место на сервере и что ночная резервная
  копия захватывает папку загрузок.
- **Свои поля файла** — автор, источник (у файла Directus уже есть название и описание).
- **Кэш скачанных копий** в GitHub Actions (см. «Кэш превью»).
- **Нынешние снимки** `static/photos/` (291): перенести скриптом или оставить, шаблон читает оба места.

## Где хранить сведения о снимках — не решено

Отложено владельцем 2026-11-11. Нужно хранить: автора (одного на серию или своего у снимка), источник (ЖЖ, ВК…),
подпись к снимку, кто на снимке, и связь снимка из галереи с событием. Что есть сейчас: в галереях «Фотографии»
(8 страниц, 99 разделов, 427 снимков) всё это записано текстом раздела — заголовок «С концерта …», строка об авторе
(одна на раздел у 86 из 99: «Автор — …, оригинал в ВК»), подписи под отдельными снимками у ≈50 (о месте: «Питер»,
«Хайфа»); у 291 снимка в `static/photos` не известно ничего, кроме концерта (папка).

Варианты:

1. **Поля у события в Directus** — `photos_author`, `photos_source`, `photos_extra` (пути к снимкам из галерей; строками
   или списком записей «путь + подпись»). Просто, но сведения из галерей повторяются в базе, а пути в базе ломаются
   при переименовании файла в репозитории.
2. **Свои таблицы в Directus** — серия снимков (`events_id`, автор, источник, вид: концерт / кулуары / слёт…),
   снимок (путь к файлу, подпись, порядок), персоналии (авторы, люди на снимках). Стандартная модель архивов; галереи
   со временем можно собирать из тех же серий. Тяжело: три новые таблицы и перенос 99 разделов; персоналии — вопрос
   шире фотографий (составители, переводчики, исполнители), решать его стоит отдельно.
3. **В самом файле** — стандарт IPTC Photo Metadata (XMP в JPEG): поля `Creator`, `Description`, `Source`,
   `Credit Line`, `Person In Image`, `Event`, место и дата. Сведения едут с файлом, правятся digiKam или exiftool,
   новых полей в базе нет. Проверка 2026-11-11: Hugo 0.164 (`.Meta`, `imaging.meta`) прочитал `Creator`, но не
   `Description`, `Event`, `Person In Image` и IPTC-поля — почему, не выяснено.
4. **Пометка в разделе галереи** — `<h2 id="msk89" data-event="L1989-E">`: шаблон каталога при сборке находит разделы
   с пометкой и берёт из них снимки (автор, источник, подписи остаются в тексте галереи, в одном месте). Ничего нового
   в базе; но шаблону придётся разбирать HTML галерей, а у снимков из `static/photos` автора записать негде.

Варианты сочетаются: например, связь с событием — папкой или пометкой в галерее (4), сведения о снимке — в файле (3).
Для снимков в хранилище Directus сведения естественно держать в полях файла (название, описание, свои поля автора
и источника); варианты выше остаются для снимков из галерей «Картинок».

**Порядок и обложка** при любом варианте: сначала свои снимки `photos/<id>/` по имени, затем снимки из галерей;
обложка — первый снимок. Отдельного поля «обложка» не нужно.

## Кэш превью в GitHub Actions

Первая обработка в Hugo — ≈0,35 с на снимок с 2000 точек; локально повторная сборка берёт готовые превью
из `resources/_gen`. В GitHub Actions этот кэш между запусками теряется — когда больших снимков станут сотни,
сохранять его (`actions/cache`), иначе каждая сборка обрабатывает всё заново. Пока все снимки не больше рамки
324×432 и выводятся как есть, превью не делаются.

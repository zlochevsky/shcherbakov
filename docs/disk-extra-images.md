# План: полноразмерные изображения дисков

Инструкция для следующей сессии. Держите при себе, но не воспринимайте как
техзадание слово в слово — сверяйтесь с пользователем на развилках.

## Что уже сделано

- Поле `sets.extra_images` (Directus, type JSON, interface Tags) заведено и
  используется.
- `layouts/miscellaneous/diskpage.html`: обложка (`album_img`/`.Params.image`)
  и доп. изображения (`extra_images`/`.Params.images`) объединены в один
  `<ul class="disk-images">` — единый ряд одинаковых карточек 220×220
  (`assets/css/disks.css`, `object-fit: contain`), без отдельной раскладки
  «обложка сверху, остальное снизу».
- **Механизм полноразмерных версий уже реализован и работает**: если для
  файла `<name>.<ext>` в `static/Images/` существует файл
  `<name>-full.<ext>`, шаблон сам оборачивает превью в
  `<a href=".../<name>-full.<ext>" target="_blank" rel="noopener">`.
  Проверка — через `os.FileExists` в шаблоне (`printf "static/Images/%s"`).
  **Никакого отдельного поля в БД для полноразмерных версий заводить не
  нужно** — соответствие целиком закодировано в имени файла. Это осознанное
  архитектурное решение: пробовали вариант с параллельным JSON-массивом
  URL-ов, отказались — слишком легко перепутать порядок между массивом
  превью и массивом полноразмерных.
- Все 32 записи `sets` в БД уже имеют `album_img` (сверено с
  `lambda.mkshch.com/Disks/<id>.html` — расхождений не было). У 21 из них
  `extra_images` уже заполнен — но **это низкое разрешение с легаси-страницы
  lambda.mkshch.com, ещё не сопоставленное с полноразмерными файлами
  магазина**.
- **`minsk4` — единственный диск, доведённый до конца по новой схеме**
  (образец для остальных, см. ниже).

## Что нужно сделать

Для всех сетов, кроме `minsk4` (список — `docs/directus.md` не хранит
диски, актуальный список смотреть прямым запросом
`GET /items/sets?fields=id,album_img,extra_images` — на момент написания
32 записи: aviapochta, balagan, balagan_1996, celoe, celoe_1997, chmuzyka1-3,
deja, drugaja, esli, eto, fauxpas, gorod, izbran1-2, kovcheg1-2, minsk1-4,
once, peshkom, pomotivam, predpolo, raycentr, shanson, vishnevo, vozdvig,
xopobod, zaklinan), для каждого:

1. Найти страницу в интернет-магазине: `https://mkshch.com/album-<slug>/`.
   Slug — транслитерация названия, но лучше не гадать, а смотреть ссылку
   «Послушать отрывки и приобрести диск» на легаси-странице
   `lambda.mkshch.com/Disks/<id>.html` (она у большинства уже есть в
   `content/Disks/<id>.md`, но надёжнее взять с самой lambda-страницы —
   `.md`-файлы этот блок не всегда копируют).
2. Скачать HTML магазинной страницы (не через WebFetch — он даёт
   AI-саммари, а не сырой HTML), найти `<img>` через
   `grep -oE '[a-zA-Z0-9_/.\-]+\.(jpg|jpeg|png|webp)'` — там будут пути вида
   `/upload/iblock/<hash>/<hash>.jpg` (Bitrix CDN).
3. **Скачать все найденные изображения** (`curl -sL "https://mkshch.com<path>"`).
4. **Визуально сопоставить каждое с уже имеющимся локальным превью**
   (`static/Images/<name>.<ext>`, взять список из `album_img` +
   `extra_images` в БД). Хэш-имена магазина никак не соотносятся с нашими —
   сопоставление только глазами (инструмент `Read` показывает картинки).
   Для minsk4 ушло 4 изображения магазина на 3 существующих превью + 1
   совсем новое (буклет с текстом, которого раньше не было ни в каком виде).
5. Для каждого сопоставленного изображения: сохранить полноразмерную версию
   как `static/Images/<name>-full.<ext>`, где `<name>.<ext>` — уже
   существующее имя превью.
6. Для изображений магазина, которым **не нашлось** локального превью
   (совсем новые, как буклет у minsk4): сохранить как
   `<новое-имя>-full.<ext>`, сгенерировать превью тем же именем без
   `-full` через ImageMagick (`magick <name>-full.jpg -resize 300x300
   <name>.jpg` — ориентироваться на 300px по длинной стороне, как у
   существующих превью) и добавить `<новое-имя>.<ext>` в `extra_images` в БД
   (через `tokenrw`, см. `docs/directus.md` про токены — читать/писать
   аккуратно, не печатать `tokenrw` в чат, см. ниже).
7. Пересобрать (`hugo -d <scratch> --cleanDestinationDir --ignoreCache`),
   проверить `<ul class="disk-images">` на странице диска — превью на
   месте, у сопоставленных есть `<a target="_blank">` на `-full`.

## Важные грабли

- **Не гадать slug/имя файла** — сопоставление изображений только визуальное,
  через `Read`. Ошибиться и связать превью одного диска с полноразмерной
  версией другого — тихая проблема, которую сложно заметить постфактум.
- **`curl` без `-g`/`--globoff` не работает с квадратными скобками в URL**
  (актуально при работе с Directus-фильтрами `filter[x][_eq]=y`, не для
  скачивания картинок, но легко забыть при смешанной сессии).
- **zsh, не bash**: `for id in $ids` с обычной строковой переменной не
  разбивается на слова (в отличие от bash) — использовать `ids=(a b c)` и
  `"${ids[@]}"`, либо `for id in a b c d ...` без промежуточной переменной.
- **`tokenrw` не печатать в текст, который увидит пользователь** — доставать
  и использовать в одной команде (`TOKENRW=$(python3 -c "...")`, дальше
  сразу в `curl -H "Authorization: Bearer $TOKENRW"`), не выводить `echo
  $TOKENRW` и не логировать его в файлы, которые потом будут прочитаны и
  показаны в чате.
- **`balagan_1996` и `celoe_1997`** — есть в БД (`sets`), но нет
  собственного `content/Disks/<id>.md` и, соответственно, непонятно, есть
  ли для них отдельная легаси/магазинная страница вообще (возможно, это
  альтернативные издания `balagan`/`celoe`, использующие тот же материал).
  Разобраться в начале, не тратить время на поиск несуществующих страниц
  вслепую — сперва спросить пользователя, что это за записи.
- Диски без доп. изображений на легаси-странице (`drugaja`, `eto`, `gorod`,
  `minsk1-3`, `shanson`, `vishnevo`) **тоже стоит проверить на магазине** —
  не факт, что там только обложка, у minsk4 расхождение было именно такого
  рода (легаси-страница показывала 3 картинки, магазин — 4).
- Объём большой: ~30 дисков × 1-4 изображения. Соглашение с пользователем на
  момент паузы — двигаться диск за диском, чтобы можно было проверять
  результат по ходу, а не одним огромным заходом.

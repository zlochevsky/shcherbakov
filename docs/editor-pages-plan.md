# План: создание страниц и разделов редактором в `/admin/` (Sveltia)

Записано 2026-10-15 по обсуждению с владельцем. Цель — удобство и свобода редактора: завести новую страницу или
раздел целиком (заголовок, адрес, вид страницы, поля для поисковиков, текст, пункт в меню), не трогая код и файлы
настроек.

## Исходное состояние

- Меню сайта — `config/_default/menus.json` (с 2026-10-15; раньше — в `hugo.json`): шесть меню (`indexheadermenu`,
  `indexfootermenu`, `searchheadermenu`, `ctgheadermenu`, `trnheadermenu`, `concertsheadermenu`); у пунктов `name`,
  `pageRef`/`url`, `weight`, `pre`/`post`, `params` (`isDateToPrint`, `dynamicLastmod`, `collapsible`, `toggleChild`,
  `mobileOnly`, `shortName`, `icon`, `dropdown`, `lang`), подменю — через `parent`/`identifier`. Выводит `layouts/partials/menu.html`.
- **Hugo сортирует меню по `weight`, а не по месту пункта в списке** — перетаскивание в списке само порядок на сайте
  не меняет. Это главная сложность для редактора.
- Пункт меню Hugo умеет задавать и во front matter самой страницы (`menus: {<меню>: {name, weight, parent, …}}`).
- В Sveltia сейчас редактируются существующие страницы; создавать можно статьи (Рецензии, Пародии, Фан-клуб) и
  страницы картинок. Поля для поисковиков (`params.seoTitle`, `description`) уже есть у этих коллекций.

## Шаг 1. Форма «Новая страница»

Коллекция в `static/admin/config.yml`, создание разрешено. Поля:

| Поле | Что задаёт |
|---|---|
| Заголовок | `title` (заголовок на странице) |
| Адрес | имя файла и `url`: `koncerty-2027` → `/koncerty-2027.html` (латиница) |
| Раздел | папка: корень сайта, фан-клуб, картинки и т. п. (список разрешённых) |
| Вид страницы | `layout` — выбор из готовых шаблонов с понятными названиями («Статья», «Страница с картинками», «Простая страница» …) |
| Заголовок и описание для поисковиков | `params.seoTitle`, `description` |
| Текст | тело (HTML; предпросмотр — как у статей: Markdown в режиме исходника) |
В меню новая страница добавляется отдельно, на экране «Порядок меню» (шаг 2): все пункты хранятся в одном
`config/_default/menus.json`, а не во front matter страниц — иначе порядок пунктов из разных файлов не собрать
перетаскиванием (решение владельца 2026-10-18).

**Виды страниц в форме** (2026-10-18; на первое время хватит первых трёх):

| Название в форме | `layout` | Что это |
|---|---|---|
| Статья | `praises-article` | страница с текстом: заголовок, автор, ссылка «назад»; годится и как «простая страница» (так сделаны `statistics`, `tab`, `kniga_pamyati`) |
| Страница с картинками | `images-page` | фон, текст по центру, ссылка «вверх» |
| Страница диска / кассеты / книги | `diskpage`, `tapepage`, `bookpage` | только при заведённой записи в Directus: данные — по её `id` |
| Страница гастролей | `archive-page` | как в «Архиве» |
| Статья на другом языке | `language-article` | в языковом разделе, с «хлебными крошками» |

Не входят: одиночные страницы корня (`bio`, `buy`, `about`, `no`, `sociology` — у каждой свой шаблон со вшитой
навигацией и цветами, по сути та же «Статья»), страницы, которые строятся из базы (каталоги, концерты, поиск,
«Словарь»), переадресации.

Перед началом: проверить сочетание «раздел ↔ вид страницы» (например, в фан-клубе — статья) и правило разделения
сайта (`docs/showcase-and-club.md`: витрина не ссылается на клуб).

## Шаг 2. Экран «Порядок меню»

Существующие пункты меню перетаскиваются мышью, порядок на сайте следует порядку в списке.

**Решение (владелец, 2026-10-18): пересчитывать `weight` по месту в списке**, меню остаются в
`config/_default/menus.json`. Sveltia при перетаскивании сохраняет только порядок в списке и `weight` не меняет, а Hugo
сортирует по `weight` (при равных — по алфавиту). Поэтому перед сборкой скрипт проставляет `weight` по месту
(10, 20, 30…) — в CI и локально; в форме пункта `weight` не показывается. Здесь же — добавление пункта для новой
страницы (шаг 1).

Отвергнутый вариант: перенести меню в файл данных (`data/menus.json`) и выводить пункты в порядке файла — пришлось бы
переписать `partials/menu.html` (подсветка текущей страницы, дата у пунктов, `mobileOnly`, выпадающие подменю).

## Шаг 3. Даты обновления в меню

Записано 2026-10-16 по обсуждению с владельцем.

### Как сейчас

Дата у пункта меню выводится, если у пункта `params.isDateToPrint: "yes"` (`menus.json`); источник даты
(`layouts/partials/menu.html`):
- `params.dynamicLastmod` — имя коллекции Directus (`works`, `translations`): самая поздняя `date_created` в коллекции;
- иначе `.Lastmod` страницы, на которую ведёт пункт: `lastmod` во front matter → время изменения файла → дата страницы
  (порядок — `frontmatter.lastmod` в `hugo.json`).

**Ошибка**: где `lastmod` пусто или нет поля, берётся время файла, а в CI это время сборки — на боевом сайте у «Новостей»
и «Книг» дата последней сборки (16.10.26 при последней новости 13.10). Время файла как источник даты убрать.

### Решение

Показ даты и её источник — **свойство страницы, а не пункта меню**: у одной ссылки во всех меню одно поведение.
- Front matter страницы: `lastmod` (дата) и `params.menuDate` (bool, «Показывать дату в меню»); дата не из `lastmod` —
  `params.menuDateFrom` (вместо `dynamicLastmod` у пункта меню): `section` (самая свежая статья раздела), `announces`
  (последнее действующее объявление), `sets` (последний из выводимых дисков), `texts` / `translations` (самая свежая
  дата публикации текста).
- Показ даты — **явный флажок** (решение владельца 2026-10-18), а не «есть дата — показываем»: `lastmod` нужен и вне
  меню (`sitemap.xml`, даты групп и пометка «новое» в шаге 4), а у дат по разделу стирать нечего — выключить их можно
  только флажком. В редакторе: флажок «Показывать дату в меню» и список «Откуда дата» (поле «Дата» по умолчанию /
  статьи раздела / объявления / диски / тексты).
- Пункт меню: необязательное `params.date: page | show | hide` («как у страницы» по умолчанию / «показывать» /
  «не показывать») — на редкий случай, когда в одном меню дату надо убрать или показать вопреки странице.
- Шаблон меню: `params.date` пункта, если задано, иначе `params.menuDate` страницы. Дата: из Directus, если задан
  `menuDateFrom`; иначе `lastmod` страницы; пусто — даты нет (не время файла и не время сборки).
- Переходный период: понимать и старое `isDateToPrint: "yes"` (строка), и логические значения флажков Sveltia.

### В редакторе (Sveltia)

- Во всех коллекциях статей — поле «Дата» (`lastmod`, `widget: datetime`, без времени: календарь и ввод с клавиатуры;
  новой статье — сегодняшняя дата) и флажок «Показывать дату в меню» (`params.menuDate`).
- У страниц с датой из базы — вместо поля «Дата» пояснение «дата — когда в базу добавлена последняя песня / последний
  перевод» и тот же флажок.
- В форме пункта меню (шаг 2) — список «Дата» с подсказкой: «дата берётся из страницы, на которую ведёт пункт
  (поле „Дата“ или база)». Само значение даты рядом с пунктом показать нельзя: форма Sveltia видит только поля
  редактируемого файла, вычисляемых полей и чтения других файлов нет.

### Страницы, которым нужна дата (сейчас с датой в меню)

| Пункт меню | Страница | Источник даты | В редакторе сейчас |
|---|---|---|---|
| Новости | `content/news.md` | `lastmod` (сейчас пусто — ошибка выше) | есть, поля даты нет |
| Магазин | `content/buy.md` | `lastmod` (2026-08-14) | нет |
| Нужно | `content/no.md` | `lastmod` (2008-01-08) | нет |
| Лог | `content/log.md` | `lastmod` (2026-10-09) | нет |
| Книги | `content/Books/gallery.md` | `lastmod` (поля нет — ошибка выше) | нет |
| Каталог песен | `content/catalogue.md` | Directus `works` | нет |
| Каталог переводов | `content/translations.md` | Directus `translations` | нет |

Страницы, которых нет в редакторе, добавить хотя бы с полями «Дата» и «Показывать дату в меню» (тело — без правки
или не показывать: у каталогов и «Лога» содержимое строит шаблон). Уточнить у владельца, каким ещё страницам нужна
дата в меню.

### Решения владельца (2026-10-16)

| Пункт меню | Дата |
|---|---|
| Новости | самая поздняя `publish_date` опубликованного объявления в Directus (`items/announces`, уже наступившая); объявлений нет — даты нет |
| Отзывы | самая свежая статья раздела (`Praises/`) |
| Фан-клуб | самая свежая статья раздела, рекурсивно (`fans/` и подразделы) |
| Диски | самая поздняя запись в таблице дисков Directus — только среди дисков, которые выводятся на сайте |
| Каталог песен, Каталог переводов | самая свежая дата публикации текста — вручную в файле каждого текста (не дата добавления в базу: существенная часть — тексты вне базы) |
| Концерты | без даты (записи событий в базе правятся и после создания) |
| Нужно | дату убрать |
| Магазин, Лог, Книги | `lastmod` страницы, вручную |
| у страницы нет даты | в меню даты нет |

Даты из базы обновляются при автоматической сборке (CI по расписанию дважды в сутки, 05:00 и 17:00 UTC, и при каждом
коммите) — отставание не больше 12 часов; при необходимости — запуск сборки из Directus при изменении записи.

Уточнено владельцем:
- **Новости** — только действующие (опубликованные и не истёкшие) объявления: нет действующих — даты нет, иначе дата
  не соответствовала бы содержимому.
- **Песни и переводы** — дата последней публикации текста: у каждого текста (`content/texts/…`, переводы
  `content/<язык>/…`) дата публикации ставится вручную в файле (в будущем — в Sveltia), у пункта раздела в меню —
  самая свежая из них (как у разделов «Отзывы» и «Фан-клуб»).

Дата в front matter — **на верхнем уровне** (`"lastmod": …` рядом с `title`), не внутри `params`: оттуда Hugo её не
берёт (так было в `Books/gallery.md` и `Disks/podrugim.md`, исправлено 2026-10-16).

### Что учесть

- **Дата сама не обновляется при правке**: Sveltia не меняет поле при сохранении; дату правят вручную (мелкая правка
  опечатки не выглядит как «обновление» — это скорее плюс).
- **Дата раздела**: для пункта-раздела (например, «Отзывы») осмысленная дата — самая свежая статья раздела, а не
  страница-оглавление; шаблон может брать максимум `lastmod` по страницам раздела (`params.menuDateFrom: section`).
- **Даты из Directus меняются только после пересборки**: сайт собирается при коммите; добавление в базу само сборку
  не запускает (нужен ручной запуск или вебхук Directus → GitHub Actions).
- Перенос нынешних `isDateToPrint`/`dynamicLastmod` из `menus.json` на страницы — разовая перекладка (семь пунктов
  выше; пункты повторяются в нескольких меню).

## Шаг 4. Самособирающиеся оглавления «Фан-клуба» и «Отзывов»

Записано 2026-10-16 по обсуждению с владельцем (выбран вариант Б).

**Проблема**: оглавления — ручной текст в теле (`content/fans/fans-index.md` и т. п.): ссылки, разнородные описания
(со ссылками внутри), даты групп вписаны руками («Эссе и стихи 21.02.21»). Шаблон не знает, какая статья в какой
группе, — посчитать дату группы и показать дату статьи нечем.

**Решение — списки собираются сами из полей статей**:
- в форме статьи (Sveltia): «Группа» (выбор: эссе и стихи, переводы, представления, иное творчество… — список групп
  раздела), «Дата» (`lastmod`), «Порядок» (`weight`), «Описание для оглавления» (`params.blurb`: свободный текст,
  Markdown/HTML, ссылки внутри можно — формат как сейчас), флажок «Новое» (`params.isNew`);
- в теле оглавления на месте списка — шорткод `{{< section-list "articles" >}}`: статьи группы по порядку — ссылка,
  описание, дата статьи, пометка «новое»; у заголовка группы — самая свежая дата группы. Всё, что не список
  (мемориальные страницы, предупреждение о спойлерах, ссылки, социология), — ручной текст тела, как сейчас;
- новая статья в одной форме — сама появляется в оглавлении с датой; даты групп и разделов всегда сходятся.

**Даты в меню и подменю «Фан-клуба»** (по папкам, через `params.menuDateFrom: section` страницы, на которую ведёт
пункт; шаг 3): «Фан-клуб» — самая свежая из всего раздела рекурсивно; «Картинки» — из раздела картинок;
«комментарии» — из СЗС; «главная» — из остального фан-клуба. «Отзывы» — самая свежая статья раздела.

**Перенос**: описания ~50 статей фан-клуба и статей «Отзывов» — из тела оглавлений в формы статей; описания
разнородные — полуручная работа (перенос — разработчик, проверка — владелец). Оглавления после переноса сверить
с нынешними (те же ссылки, те же описания, тот же порядок).

**Пометка «новое»** (решение владельца 2026-10-16) — у песен и у статей разный принцип:
- **статьи «Отзывов» и «Фан-клуба»** — автоматически: новая, если «Дата» (`lastmod`) не старше N месяцев; ручного
  флажка нет. N настраивается в Sveltia — отдельный файл настроек сайта (например, `data/settings.json`, коллекция-файл
  с числовым полем «Новизна статей, месяцев»); не в `config/_default/params.json` — тот не в репозитории (токен);
- **песни** — «новая, пока не вышла в исполнении на диске», но с исключениями — флажок ставится вручную; остаётся
  в Directus (`works.is_new`). В Sveltia так же удобно не сделать: список записей там только для просмотра
  (сортировка, фильтр, пометка в подписи — да; переключить флажок одним кликом в списке — нет, массовой правки нет;
  каждое изменение — открыть запись, сохранить, отдельный коммит и сборка). В Directus — таблица с колонкой,
  сортировкой и массовой правкой.

**Как:**
- поля — по виду страницы: у статей (`praises-article`) — набор «Отзывов»; у дисков, кассет, книг, циклов — заголовок,
  дата (шаг 3), свёрнутые «Параметры» (`id` только для чтения — связь с Directus), SEO-поля, текст;
- `kom`, `kom2` — расширить фильтр «Фан-клуба» или отдельные записи-файлы;
- `preview_path` — по `url` страницы, как у статей;
- проверить, что Sveltia не переписывает при сохранении поля, которых нет в форме (порядок ключей, `sitemap`,
  `params` вне формы), — на одной странице каждого вида до массового включения.

**Связь с шагами 1 и 3:** дата обновления в меню (шаг 3) нужна в том числе этим страницам — поле «Дата» в их формах
вводится заодно; виды из таблицы — кандидаты в список «Вид страницы» формы шага 1.

## Ограничение

Новый **вид** страницы (новый шаблон) редактор создать не может — это код. Он выбирает из готовых; новый вид добавляет
разработчик, после чего тот появляется в списке «Вид страницы».

# Инструкция: перенос «Словаря заморских слов» в БД

Инструкция для следующей сессии. Держите при себе, но не воспринимайте как
техзадание слово в слово — по многим пунктам решения принимались по ходу
дела в диалоге с пользователем, сверяйтесь с ним на развилках.

## Контекст

Источник — `kom.html`/`kom2.html` с `lambda.mkshch.com/fans/` (оригинальный
двухстраничный словарь примечаний и комментариев к песням М. Щербакова, 284
статьи/песни, ~900+ отдельных датированных заметок внутри них). Переносится
в Directus (коллекции `comments`/`works_see_also`) и выводится на реальной
странице `fans/kom.html` в стиле каталога — с поиском, кросс-теговой
подсветкой совпадений и сворачиванием статей по умолчанию.

    стиль `.comment-body dfn { font-style: italic }`;
  - `editor-aside` — оформление снимаем, реплику выносим следующим `<p>`; `reader-quote` внутри `<blockquote>` снимается автоматически,
    остальное — вручную (в алгоритме предупреждение «СТИЛЬ …»); подпись редактора — «— Ред.»;
  - пробелы: после `.,:` перед подписью/датой/ссылкой, после `(`, перед `)`, внутри `<a>` и `entry-date`; латинские двойники в русских

- **Порядок работы по году** (повторять для каждого): `python3 workfiles/slovar-import-year.py <год> --dry-run` → прочитать нормализованные

## Гранулярность импорта — решено

Одна статья словаря = **одна запись `comments`** (всё тело статьи целиком
как один HTML-блоб в `body`), НЕ разбиение на отдельные датированные
заметки внутри одной песни. Причина: надёжного механического способа
разделить заметки внутри статьи нет — где-то это `)</p>` после подписи,
где-то заметка обрывается без `</p>`, где-то один автор через голый `<p>`
даёт несколько примеров подряд одной подписью на всех. `sort_order`/
`author_name`/`author_contact`/`date_added` в общем случае остаются `null`
(это поля НА УРОВЕНЬ ЗАМЕТКИ, а не статьи) — заполняются только когда
статья разбирается вручную (как в «Особых случаях» ниже) и там реально по
смыслу одна запись = одна заметка с известным автором/датой.

### Импорт оставшихся статей — по одному году за раз

Готов рабочий скрипт `workfiles/slovar-import-year.py` (не псевдокод —
реально проверен: dry-run, живой импорт на 1981 годе — id=14, `kolesa`, — и
повторный запуск того же года для проверки идемпотентности, дублей не

```

python3 workfiles/slovar-import-year.py 1985 --dry-run   # посмотреть, что уйдёт
```

- никогда не трогает 4 многосоставные статьи (см. «Особые случаи» ниже) —
  они в списке `MANUAL_ANCHORS` внутри скрипта;
- уже импортированные ранее статьи (`kolesa1981` + 8 особых случаев + 5
  пилотных) при последующих запусках скрипт увидит через API и пропустит

### (Опционально, по желанию) Разметка цитат внутри заметок

Не начато, приоритет ниже основного импорта. Встроенные цитаты из **чужих**
произведений внутри тела заметок размечены непоследовательно (местами
`<i>`, местами без разметки) — можно привести к единому `<em>` по ходу
чтения каждой статьи при импорте (не отдельным проходом — дублировать
работу нет смысла). **Осторожно**: большинство `<i>` в файле — это цитаты
из САМОЙ обсуждаемой песни (ранних вариантов и т.п.), не из чужих
произведений — их трогать не надо, отличать по контексту. Аналогично `<b>`
внутри тела заметки, где это смысловое выделение (не заголовок статьи, там
`<b><a href=...>Название</a></b>` — не трогать) → `<strong>`.

## Схема БД

- **`comments`** — `id` (integer, auto-increment PK), `work_id`→`works`
  (M2O, `on_delete: SET NULL`), `excerpt` (text, nullable — цитата из
  песни), `body` (text/HTML — заметка/статья целиком), `author_name`
  (string, nullable), `author_contact` (string, nullable — mailto/URL),
  `date_added` (date, nullable), `legacy_anchor` (string — исходный `id`
  статьи), `source_page` (string, `kom`/`kom2`), `sort_order` (integer, в
  общем импорте не используется — см. «Гранулярность» выше).
  **Интерфейс поля `body` в Directus — `input-code` (не WYSIWYG!)** —
  переключено умышленно: TinyMCE при сохранении из визуального режима может
  тихо выбросить незнакомые ему кастомные классы (`entry-date`,
  `reader-quote`, `editor-aside`) — риск обсуждался с пользователем и решён
  именно так, не настройкой `extended_valid_elements`. Если когда-нибудь
  понадобится вернуть WYSIWYG — сначала явно прописать эти классы в
  allowlist TinyMCE, иначе первое же ручное сохранение в редакторе испортит
  данные необратимо.
- **`works_see_also`** — `id` (integer, auto-increment PK), `work_id`→`works`
  (M2O, статья-источник), `related_work_id`→`works` (M2O, статья-цель).
  Только прямое направление хранится, см. выше.

Обе коллекции: права на чтение роли `ReadOnly` выданы явным
`POST /permissions` (иначе сборка сайта видит пустые данные — см. грабли).

## Фронтенд (`fans/kom.html`) — построен и работает

- `content/fans/kom.md` — сама страница (заменила старый брошенный
  draft-стаб с несуществующим шорткодом `{{< datum >}}`), преамбула из
  редакторского вступления словаря.
- `layouts/miscellaneous/kom.html` — layout. Заголовок песни считается тем
  же способом, что в `catalogue.html` ($name/$year с учётом `edit`,
  math.Abs для отрицательных/неточных дат). Год выводится как в
  `catalogue.html`: `1981, 1986`, если есть `edit`.
- `layouts/partials/directus-comments.html` — тянет все `comments`
  (`limit=-1`); **явно перечисляет нужные поля** в `fields=` — если в
  будущем понадобится ещё какое-то поле из `comments`, не забыть добавить
  сюда, иначе API его просто не вернёт (см. грабли).
- `assets/css/kom.css` — стили; в т.ч. впервые описаны классы `entry-date`
  (красный, как в оригинале), `reader-quote`, `editor-aside`, которых в CSS
  вообще не было до этой сессии.
- **Поиск** — по name/incipit/году/тексту заметки, одна нормализованная
  строка на карточку (`normalize()`: casefold + NFD + снятие диакритики +
  ё→е), AND по словам через пробел, как в `catalogue.html`.
- **Кросс-теговая подсветка** — свой `TreeWalker`, без `mark.js` (сайт
  принципиально без внешних JS-зависимостей). Есть отдельная функция
  `normalizeKeepLength()` (без `.trim()`) специально для построения карты
  смещений — обычная `normalize()` с `trim()` тут ломает офсеты, см. грабли.
- **Сворачивание** — `<details>`/`<summary>`, свёрнуты по умолчанию,
  разворачиваются при совпадении фильтра. Ручной клик по карточке —
  `scrollIntoView({behavior:"instant"})`, но только когда фильтр пуст (при
  поиске одновременно открывается несколько карточек — прыгать к одной
  произвольной не нужно).
- **Колонки** (`#artlist`, брейкпойнты как в `catalogue.html`, от 100em) —
  при наличии хотя бы одной открытой карточки JS добавляет
  `#artlist.no-columns` (`column-count: 1`), иначе `column-span` у открытой
  карточки перекраивает порядок соседних карточек по колонкам — см. грабли.
- **Преамбула** — отдельный `<details class="preamble-toggle">` НАД формой
  фильтра (не между фильтром и результатами), свёрнута по умолчанию,
  заголовок сам переключается "Прочесть перед первым использованием" ↔
  "Скрыть" (CSS `[open]`), плюс вторая ссылка "Скрыть" в конце преамбулы
  (JS, поскольку нативный `<details>` не закрывается изнутри содержимого).
- Автор/дата из отдельных полей (`author_name`/`author_contact`/
  `date_added`) рендерятся в конце заметки как `(Автор, DD.MM.YYYY.)`,
  автор — ссылкой, если есть `author_contact`; используется только там, где
  эти поля реально заполнены (особые случаи выше) — при обычном импорте
  подпись уже находится внутри `body` как обычный текст, дублирования не
  будет.

## Важные грабли

- **Парсер молча возвращает 0 статей, если сменился стиль кавычек
  атрибутов в исходнике.** Ровно так и случилось в этой сессии: после
  перевода `href="..."` → `href='...'` по всему файлу (отдельная задача про
  «ёлочки») `slovar-parse.py` перестал находить вообще всё, включая
  `<a id="...">`-анкоры — его регулярки жёстко зашиты под конкретный тип
  кавычек. Чинится за минуту (поменять `"` на `'` в двух regex внутри
  скрипта), но легко не заметить и решить, что в исходнике что-то сломалось
  по-крупному. Первым делом при `0 статей` — сверить стиль кавычек.
- **Парсер: не используйте наивный regex для тела статьи.** Первая версия
  (`<ul><p>(.*?)</p></ul>` нежадным regex) молча обрезала статьи со
  вложенным `<ul>` (цитаты-в-цитате, например про Достоевского) на первом
  же внутреннем `</p></ul>`, теряя хвост статьи. `workfiles/slovar-parse.py`
  уже использует правильный, учитывающий вложенность разбор (стек глубины
  `<ul>`/`</ul>`) — пользоваться им, не переписывать заново.
- **HTML-парсер, а не просто счётчик тегов, для проверки валидности.**
  Regex-подсчёт `<tag>` vs `</tag>` не ловит перекрёстное закрытие
  (`<a><b></a></b>`). `workfiles/slovar-parse.py` использует
  `html.parser.HTMLParser` со стеком — держите эту проверку при любых
  будущих правках `slovar-merged.html`.
- **Directus API `fields=` — только то, что явно перечислено.** Забытое
  поле в `fields=` партиала — не ошибка, а молча пустой результат на
  фронтенде (так был потерян рендеринг author/date до отдельного фикса).
- **`resources.GetRemote` кэш до 10 минут** (`hugo.json →
  caches.getresource.maxAge`) — после правки данных в Directus страница
  может не обновиться сразу, это не баг фронтенда.
- **TreeWalker + подсветка: не используйте `.trim()` в функции, строящей
  карту смещений.** Текстовые узлы почти всегда начинают с отступа разметки
  (`\n  Текст...`), `trim()` сокращает их при построении общей строки для
  поиска, но карта смещений считается по нетронутой длине узла — рассинхрон
  сдвигает подсветку. Нужна отдельная функция без `trim()` именно для этого
  места (`normalizeKeepLength()` в `kom.html`).
- **TreeWalker: отбрасывайте узлы, чей `trim()` пуст**, а не просто
  `node.nodeValue.length`. Иначе whitespace-only узлы между шаблонными
  `<div>` попадают в диапазон подсветки на границе с реальным совпадением и
  дают пустой `<mark>` с цветным фоном (видимый "пустой абзац").
- **`column-span: all` у открытого `<details>` внутри multi-column списка
  — плохая идея для интерактивного разворачивания.** Каждое открытие
  создаёт разрыв сегмента, и браузер пересчитывает балансировку колонок
  заново для контента "до" и "после" — соседние карточки визуально
  перепрыгивают в другую колонку. Надёжнее — JS-класс, отключающий
  `column-count` целиком, пока открыта хотя бы одна карточка.
- **WYSIWYG (TinyMCE) в Directus может тихо портить кастомные классы при
  сохранении.** Решение — не настройка allowlist, а смена интерфейса поля
  `body` на `input-code` (уже сделано). Не переключать обратно на
  `input-rich-text-html`, не прописав сначала `extended_valid_elements`.
- **`sed` с `#` как разделителем ломается**, если в паттерне/замене есть
  `#` (URL-фрагменты, `#FF0000`) — использовать `sed -i 's|...|...|g'`.
- **Directus: создание коллекции/поля/связи через RW-токен НЕ даёт прав на
  чтение ролям.** После `POST /collections`/`/fields`/`/relations` —
  обязателен отдельный `POST /permissions` с `{"collection": "...",
  "action": "read", "fields": ["*"], "policy": "<id ReadOnly>"}`. ID
  политики `ReadOnly` на момент этой сессии —
  `7a949c6a-bad5-40cb-ba23-12251eaa7a3b` (перепроверить через
  `GET /policies`, сверить `name`).
- **Архивные редакции песен не получают своей `works`-записи** — `work_id`
  в любой связанной таблице указывает на канонический id. Если нужно
  сослаться на конкретную архивную редакцию — см. приём с
  `cycles_entries.page_id`, воспроизводим и для `comments`, если понадобится.
- **Не гадать по префиксу id** — сверять по точному совпадению
  name/incipit **и** года (несколько раз совпадение по первым буквам вело
  не туда).
- **Не reproducировать текст самих песен** — вся эта работа про
  структурную/метаданные-работу и про содержимое Словаря (комментарии, не
  сами песни). Тексты песен — только через `assets/texts/*.txt`,
  пользователь кладёт сам.
- **При массовом создании >~20 файлов разом** (актуально не для импорта
  `comments`, а если снова понадобится создавать много content-файлов) —
  Hugo dev-server может не подхватить пачку через fsnotify. Лечится `touch`
  всех файлов разом после паузы; 200 у первых проверенных файлов — не
  сигнал об успехе всей партии.
